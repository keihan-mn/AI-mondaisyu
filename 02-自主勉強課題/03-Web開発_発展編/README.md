# Web開発発展編・自習問題

この教材は、HTML・CSS・JavaScriptの基礎を学んだ人が、現在のWebアプリ開発で使われるフレームワーク、コンポーネント設計、ルーティング、データ取得、API設計、データベース、認証・認可、セキュリティ、テスト、パフォーマンス、アクセシビリティ、デプロイと運用を学ぶための学習問題です。

具体例にはTypeScript、React、Next.jsを使います。ただし、特定のコマンドや書き方を暗記することが目的ではありません。「どの技術が何を担当するのか」「なぜその設計にするのか」「問題が起きたときにどこを確認するのか」を、実行結果と自分の言葉で説明できることを目指します。

フレームワークの仕様は更新されるため、古い解説記事だけでなく、学習時点の公式ドキュメントも確認してください。

## 回答するときの共通ルール

各問題について、次の内容を含めて回答してください。具体例、比較、自分の判断は、問題文で求められたものについて書いてください。

1. 調べて分かったこと
2. 初心者にも伝わる、自分の言葉での説明
3. 実際に実行した問題では、操作、確認した結果、発生したエラーと修正内容
4. AIにコード生成や修正を依頼した場合は、主な依頼文と、提案を自分で確認した方法
5. 参考にした情報源。できるだけ公式ドキュメントを一つ以上含める

練習用プロジェクトは、既存の大切なファイルを上書きしない場所へ作成してください。コマンドを実行する前に、現在のフォルダーと、作成または変更されるファイルを確認してください。

`.env`の内容、データベース接続文字列、APIキー、Cookie、セッション識別子、パスワードなどの秘密情報を、回答、スクリーンショット、AIへの依頼文に含めないでください。必要な場合は`[REDACTED]`などに置き換えます。

## 第1章　モダンなWeb開発環境とフレームワーク

この章では、基礎編で作成したHTML・CSS・JavaScriptのページが、現在のWeb開発でどのような道具と仕組みを使って開発されるかを学びます。

### 問題1：ライブラリ・フレームワーク・ビルドツールは何が違うのか

開発に役立つ機能をまとめたものを「ライブラリ」、アプリ全体の構成や開発の進め方を支える枠組みを「フレームワーク」、開発用のコードをブラウザーで配信・実行しやすい形へ変換する道具を「ビルドツール」と呼びます。実際の製品は複数の役割を持つことがあるため、名称だけでなく機能を確認することが大切です。

React、Next.js、Viteをそれぞれ調べ、次の点を整理してください。

- 主に何を解決する道具か
- HTML・CSS・JavaScriptだけで作る場合と比べて、何が行いやすくなるか
- その道具を導入することで、新たに学ぶ必要があることや、管理するものは何か

ReactとNext.jsとViteは、同じ役割を持つ三つの代替品ではありません。Next.jsがReactを使ってUIを作るフレームワークであることや、ReactアプリをNext.jsで構成する場合とViteを使って構成する場合の関係も整理してください。

そのうえで、「自己紹介を1ページだけ公開する」場合と、「ログイン後に複数の画面でタスクを管理する」場合について、どの道具を使うか、または使わないかを理由とともに判断してください。この判断には、サイトの規模や開発者の経験によって複数の考え方があります。

> **ヒント：**「React library official」「Next.js framework official」「Vite build tool official」「ライブラリ フレームワーク 違い」というキーワードを使って調べてください。

### 問題2：Node.js・npm・TypeScriptは開発中に何をしているのか

モダンなWeb開発では、ブラウザー以外の場所でJavaScriptを実行できるNode.jsや、外部パッケージとコマンドを管理するnpmがよく使われます。TypeScriptは、コードの実行前に値の種類である「型」の不整合を見つけやすくする、JavaScriptを拡張した言語です。

次の項目を調べ、開発中とブラウザーで表示するときに、それぞれがどのように関係するか説明してください。

- Node.js
- npm
- `package.json`
- `package-lock.json`
- `node_modules`
- TypeScriptと`tsconfig.json`
- `npm run dev`と`npm run build`

また、`package.json`と`package-lock.json`の違い、`node_modules`をGitで管理しないことが多い理由、TypeScriptの型エラーとブラウザー実行中のエラーの違いを、初心者向けに整理してください。

`dev`や`build`という名前のコマンドが、npmによってすべてのプロジェクトで同じ意味に決められているのか、それとも`package.json`の`scripts`によってプロジェクトごとに定義されるのかも確認してください。

最後に、AIから「エラーを解決するため、このパッケージを追加してください」と指示された場合、実行前に何を確認するかを、パッケージの目的、公式情報、変更されるファイルの観点からチェックリストにしてください。

> **ヒント：**「Node.js official about」「npm package.json package-lock.json」「npm dependencies node_modules gitignore」「TypeScript static type checker」「npm run dev build 違い」というキーワードを使って調べてください。

### 問題3：フレームワークのプロジェクトを起動し、変更を確認しよう

練習用の新しいフォルダーで、学習時点のNext.js公式ドキュメントを参考に、TypeScriptとApp Routerを使うプロジェクトを作成してください。セットアップツールの質問や既定値はバージョンによって変わることがあるため、選んだ項目とその理由を記録してください。

Node.jsとNext.jsのバージョンも記録し、インストールされたNext.jsのバージョンに対応する公式ドキュメントを確認してください。

プロジェクト作成後に、次の操作を一つずつ行います。

1. 開発サーバーを起動し、ターミナルに表示されたURLをブラウザーで開く
2. 最初のページを表示するファイルを特定し、見出しを「タスク管理アプリ」へ変更する
3. 保存後の画面変化と、ターミナルおよびブラウザーのConsoleにエラーがないことを確認する
4. 開発サーバーを停止し、停止後に同じURLを開いたときの結果を確認する
5. 開発サーバーを再起動し、保存した変更が残っているか確認する
6. 本番用ビルドを実行し、成功したか、またはどのようなエラーが発生したかを確認する

実行したコマンドの目的と、主に変更したファイルを説明してください。エラーが発生した場合は、エラー文を消すことだけを目的にせず、どの操作で、どのファイルに関する問題が起き、どの修正で解決したかを記録してください。

> **ヒント：**「Next.js installation App Router TypeScript official」「create-next-app options」「Next.js development server」「Next.js production build」「Next.js Fast Refresh 自動反映」というキーワードを使って調べてください。

## 第2章　コンポーネント設計と状態管理

Reactでは、ボタン、入力欄、カード、ページなど、UI（利用者が見たり操作したりする画面）を「コンポーネント」という部品に分けて作ります。この章では、単にファイルを細かく分けるのではなく、役割とデータの流れを考えてUIを設計します。

### 問題1：画面をどのようにコンポーネントへ分けるのか

次の要件を持つタスク管理画面を作るとします。

- 画面上部にアプリ名と未完了件数を表示する
- タスク名を入力して追加できる
- 「すべて」「未完了」「完了」で絞り込める
- タスクを一覧表示する
- 各タスクに、完了状態を切り替えるボタンがある

この画面をコンポーネントへ分け、親子関係が分かるツリーとして表してください。各コンポーネントについて、次の内容を整理します。

- 担当する表示または操作
- 他の画面でも再利用する可能性があるか
- 修正の理由が一つにまとまっているか

「画面全体を1つのコンポーネントにする」方法と、「表示する文字ごとに非常に細かく分ける」方法の問題点も比較してください。最後に、自分が分割の単位を判断するときの基準を三つ以内にまとめてください。この問題では部品分けと役割に集中し、データと操作を親子間で伝える方法は問題2と3で扱います。唯一の正解はありませんが、各部品の役割を説明できる必要があります。

> **ヒント：**「React Thinking in React component hierarchy」「React component 分割 基準」「UI 役割ごと 部品化」「React UI tree」というキーワードを使って調べてください。

### 問題2：PropsとTypeScriptの型で、再利用できるタスク表示を作ろう

Reactで親コンポーネントから子コンポーネントへ渡す値を「Props」といいます。次の`TaskCard`は、タスクの名前と完了状態をPropsとして受け取るコンポーネントです。

```tsx
type TaskCardProps = {
  title: string;
  completed: boolean;
};

export function TaskCard({ title, completed }: TaskCardProps) {
  return (
    <article>
      <h2>{title}</h2>
      <p>{completed ? "完了" : "未完了"}</p>
    </article>
  );
}
```

このコードについて、`TaskCardProps`、`string`、`boolean`、`{ title, completed }`、三項演算子の各部分が何を表すか説明してください。

次に、第1章で作成したプロジェクトへこのコンポーネントを追加し、少なくとも3件の異なるタスクを表示してください。その後、期限を表す`dueDate`をPropsに追加し、三つのタスクのうち一つは期限が未定であることを型で表現してください。期限がない場合の型と表示方法には複数の選択肢があるため、自分が選んだ方法と理由を説明します。

意図的に`completed="yes"`のような間違った値を渡し、エディター、開発サーバーの表示、ブラウザー、本番用ビルドのそれぞれで、どのような結果になるかを記録してください。TypeScriptの型情報がJavaScriptの実行時にはそのまま残らないことも調べ、型検査と実行時の値の扱いを比較します。確認後は正しいコードへ戻してください。

> **ヒント：**「React passing props official」「TypeScript object type optional property」「TypeScript string boolean」「React conditional rendering official」「TypeScript props React」というキーワードを使って調べてください。

### 問題3：Stateとイベントを使って、表示を操作できるようにしよう

Reactの「State」は、入力中の文字や選択中のフィルターなど、利用者の操作によって変化し、画面が記憶しておく必要のある情報です。タスク管理画面へ次の機能を順番に追加してください。

実装前に、次の項目を公式ドキュメントのサンプルを動かしながら確認してください。

- 配列の`map()`で各タスクをコンポーネントへ変換する方法
- 一覧の各要素に、順番が変わっても同じ要素を識別できる`key`を与える理由
- 文字入力の値をStateと`onChange`で管理する「制御された入力」
- 既存のStateの配列やオブジェクトを直接書き換えず、新しい値を作って更新する方法
- タスクの表示名とは別に、各タスクを安定して識別するIDを持たせる理由

たとえば、タスク1件の形を次のようにし、一覧は`Task[]`として扱えます。`id`の生成に配列の現在位置をそのまま使う場合と、追加時に一度だけ一意なIDを作る場合の違いも考えてください。

```tsx
type Task = {
  id: string;
  title: string;
  completed: boolean;
};
```

1. タスク名を入力する欄を作る
2. 追加ボタンを押すと、入力したタスクが一覧に追加されるようにする
3. 空白だけのタスクは追加しない
4. 各タスクのボタンで、完了と未完了を切り替えられるようにする
5. 未完了のタスク件数を表示する

Next.jsのApp Routerで`useState`やクリックイベントを使うコンポーネントは、ブラウザー側で動くClient Componentにする必要があります。学習時点の公式ドキュメントで、`"use client"`を書く場所と、どのコンポーネントへ必要かを確認してください。

実装前に、「タスクの一覧」「入力中の文字」「未完了件数」のどれをStateとして保持し、どれを他の値から計算するかを予想します。実装後は実際のコードと比較し、同じ意味の情報を複数のStateとして持つとどのような不整合が起こり得るか考えてください。

最後に、データがPropsとして親から子へ渡る流れと、子で行われた操作を関数で親へ伝える流れを、矢印を使って図にしてください。

> **ヒント：**「React state component memory official」「React rendering lists key」「React updating arrays in state」「React sharing state between components」「Next.js use client Client Component」というキーワードを使って調べてください。

## 第3章　ルーティング・レンダリング・データ取得

「ルーティング」とは、URLと表示するページを対応させる仕組みです。「レンダリング」とは、データとコードから画面に表示する結果を作ることです。この章では、複数ページの構成、サーバーとブラウザーの役割分担、データの待ち時間や失敗も含む表示を学びます。

### 問題1：URLとファイル構成はどのように対応するのか

Next.jsのApp Routerでは、`app`フォルダー内のフォルダーと特別なファイル名を使い、URLとページの対応を表します。ファイル構成でURLを定める方式を「ファイルシステムルーティング」といいます。

次のURLを持つタスク管理アプリについて、App Routerのフォルダーとファイルの構成をディレクトリツリーで設計してください。

- `/`：アプリの説明を表示する
- `/tasks`：タスク一覧を表示する
- `/tasks/123`：IDが`123`のタスク詳細を表示する
- `/settings`：設定画面を表示する

次に、プロジェクト作成時に生成されたルートの`layout.tsx`を確認し、`html`要素と`body`要素を残したまま、すべてのページでアプリ名とナビゲーションを共通表示するように編集してください。セットアップ時に`src`フォルダーを使う選択をした場合は、`app`ではなく`src/app`が起点になることに注意します。`page.tsx`、`layout.tsx`、`[id]`の名前がそれぞれ何を表し、`/tasks/123`の`123`に相当する値をどのように受け取るかも、学習時点の公式ドキュメントで確認します。古い記事と書き方が異なる場合は、使用中のNext.jsバージョンに対応する公式ドキュメントを優先してください。

実際に各ページを作成し、ナビゲーションから移動して、ブラウザーのURLと表示内容を記録してください。HTMLの`<a>`要素とNext.jsの`Link`コンポーネントによるページ移動も比較し、アプリ内の移動でどちらを使うかを理由とともに説明してください。

> **ヒント：**「Next.js App Router layouts pages official」「Next.js file-system routing」「Next.js dynamic segments params」「Next.js Link component navigation」というキーワードを使って調べてください。

### 問題2：サーバーとブラウザーのどちらで画面を作るのか

Webアプリの表示結果は、主にサーバー側で作ってからブラウザーへ送ることも、ブラウザー側でJavaScriptを使って作ることもできます。「サーバーサイドレンダリング（SSR）」「静的サイト生成（SSG）」「クライアントサイドレンダリング（CSR）」について、次の観点から比較してください。ここでのクライアントはブラウザーを指します。

- 主な表示結果をどこで、どのタイミングで作るか
- ページを最初に開いた利用者に、内容が届くまでの流れ
- 表示内容が更新されるタイミング
- ブラウザーへ送るJavaScriptと、利用者の操作との関係

また、Next.js App RouterのServer ComponentとClient Componentは、SSRとCSRの別名ではありません。両者が「コンポーネントのロジックをどの環境で扱い、どの機能を使えるか」に関する分類であることを調べてください。Client Componentであっても、最初の読み込みではサーバー側でHTMLが事前レンダリングされ、ブラウザーで「ハイドレーション」と呼ばれる処理が行われた後に操作可能になる場合があります。この流れを調べ、Client ComponentとCSRを同じものと考えると何を誤解するか説明してください。

`useState`、クリックイベント、`localStorage`、サーバーだけが知るデータへのアクセスについて、どちらのコンポーネントが適しているかを理由とともに整理します。

最後に、次のページをどの表示方式とServer・Client Componentの組み合わせで作るか、自分の案と理由を書いてください。この問いには、更新頻度や利用者体験の優先順位によって複数の判断があります。

- 全利用者が同じ内容を読む利用規約ページ
- 開くたびに最新在庫を表示したい商品ページ
- 文字を入力するたびに、取得済みのタスクを絞り込む画面

> **ヒント：**「SSR SSG CSR 違い」「Next.js rendering static dynamic」「Next.js Server Components Client Components official」「use client browser APIs」「React hydration」というキーワードを使って調べてください。

### 問題3：データ取得の成功以外も考えた画面を作ろう

Webアプリがデータを読み込むときは、すぐに成功してデータが表示される場合だけでなく、読み込み中、データが0件、取得失敗という状態があります。次の4状態について、利用者に何を表示し、どの操作を用意するかを設計してください。

1. データを読み込んでいる
2. 1件以上のタスク取得に成功した
3. 取得に成功したが、タスクが0件だった
4. 通信やサーバーの問題で取得に失敗した

練習では、データベースや本物のAPIをまだ作らず、タスク配列を非同期で返す練習用の`getTasks()`関数を用意してください。「非同期」とは、データ取得などの完了を待つ間も、他の処理をすべて止めないための考え方です。

次の順序で、`/tasks`ページに各状態の表示を実装します。

1. `getTasks()`がタスクを返す場合を実装する
2. `getTasks()`が空の配列を返す場合を作り、「まだタスクがありません」と次の操作を表示する
3. 意図的に待ち時間を作り、`/tasks`以外のページから`Link`で移動して、読み込み中の表示を確認する
4. 意図的にエラーを発生させ、利用者向けのメッセージを表示する。再試行機能も作る場合は、エラーの原因を解除してから再試行できる手順にする
5. 確認後、意図的に追加した待ち時間とエラーを元に戻す

Next.js App Routerの`loading.tsx`と`error.tsx`がそれぞれどの状態を扱うファイルかを調べ、この練習で使った場所を説明してください。`error.tsx`にClient Componentの指定が必要な理由と、現在使っているNext.jsバージョンでの再試行方法も公式ドキュメントで確認します。

また、開発者が調査するための詳細なエラー情報と、利用者へ表示するメッセージをそのまま同じにすると、どのような問題が起こり得るか考えてください。成功時の画面だけでなく、四つの状態をどのように確認したかをチェックリストにしてください。

> **ヒント：**「Next.js fetching data official」「Next.js loading UI error handling」「React loading error empty state」「Next.js error.tsx Client Component」「Next.js production error message server log」というキーワードを使って調べてください。

## 第4章　使いやすいAPIの設計

API（Application Programming Interface）は、別のプログラムから機能やデータを利用するための接続口です。この章では、タスク管理アプリの画面から利用するHTTP APIを設計し、リクエストとレスポンス、入力値の検証、仕様書による契約の共有を学びます。

### 問題1：タスクを操作するURLとHTTPメソッドを設計しよう

APIが公開する個々の接続先を「エンドポイント」といいます。HTTPメソッドは、その接続先に対して取得、作成、変更、削除など、何をしたいかを表します。

まず、`GET`、`POST`、`PUT`、`PATCH`、`DELETE`の用途と、`PUT`と`PATCH`の違いを調べてください。次に、タスク管理アプリの次の操作について、「HTTPメソッド」「URL」「リクエストで渡す値」「成功時のステータスコード」「レスポンスの例」を表にしてください。

- タスクを一覧で取得する
- 新しいタスクを作成する
- IDを指定して1件のタスクを取得する
- 指定したタスクの完了状態だけを変更する
- 指定したタスクを削除する

URLは`/api/tasks`と`/api/tasks/{id}`を候補にし、`{id}`には実際のタスクIDが入るものとします。`200 OK`、`201 Created`、`204 No Content`、`400 Bad Request`、`404 Not Found`、`500 Internal Server Error`がそれぞれ何を表すかを調べ、成功時だけでなく、入力間違いや存在しないIDに対するレスポンスも設計してください。

`201 Created`では作成したデータのURLを`Location`ヘッダーで示せること、`204 No Content`のレスポンスには本文を含めないことも確認してください。また、壊れたJSON、JSON以外のContent-Type、JSONの形は正しいが値が要件を満さない場合に、`400`、`415`、`422`などをどのように使い分けるか、自分のAPIの方針を決めてください。

最後に、`/api/createTask`、`/api/updateTask`、`/api/deleteTask`のように操作ごとのURLを作る案と、タスクという対象を表すURLにHTTPメソッドを組み合わせる案を比較してください。自分ならどちらを選ぶか、URLから目的を予想しやすいか、操作を追加しやすいかという観点から理由を書いてください。

> **ヒント：**「HTTP request methods RFC 9110」「REST API resource URL design」「PUT PATCH 違い」「HTTP status code 200 201 204 400 404 500」というキーワードを使って調べてください。

### 問題2：Route HandlerでAPIを作り、不正な入力も扱おう

Next.js App RouterのRoute Handlerは、`route.ts`にHTTPメソッドと同じ名前の関数を用意し、HTTPリクエストを処理する仕組みです。この問題では`app/api/tasks/route.ts`、`src`フォルダーを使っている場合は`src/app/api/tasks/route.ts`へ作成します。

データベースはまだ使わず、練習用の配列をサーバー側のデータとして使います。配列の内容は、サーバーの再起動だけでなく、開発中の自動再読み込み、複数プロセス、サーバーレス環境などでも保持される保証がありません。実用的な保存先ではないことと、使用中のNext.jsバージョンでどのように実行・キャッシュされるかを確認してください。

第4章の問題1で設計した内容をもとに、次の二つを実装してください。

1. `GET /api/tasks`：タスク一覧をJSONで返す
2. `POST /api/tasks`：JSONで受け取ったタスクを追加し、作成したタスクを返す

`POST`では、リクエスト本文がJSONとして読み取れるか、`title`が文字列か、空白を除いて空でないか、許可する最大文字数を超えていないかをサーバー側で検証します。画面側で同じ検証をしていても、API側の検証が必要な理由を説明してください。

ブラウザーのNetworkパネル、APIクライアント、または`curl`などのうち、自分が内容を説明できる方法を使って、次のケースを確認します。コマンドはコピーするだけでなく、URL、HTTPメソッド、ヘッダー、本文がどの部分かを説明してください。

- 正常に一覧を取得できる
- 正常な`title`でタスクを作成できる
- JSONとして壊れた本文を送る
- `title`がない、文字列でない、空白だけ、または長すぎる本文を送る

各ケースのステータスコードとJSONを記録し、正常時とエラー時でレスポンスの形をどのように統一すると画面側が扱いやすいか考えてください。

> **ヒント：**「Next.js Route Handlers official」「Request json Response json Web API」「API server-side input validation」「HTTP Content-Type application json」「DevTools Network API response」というキーワードを使って調べてください。

### 問題3：OpenAPIでAPIの契約を書き、変更の影響を考えよう

APIの「契約」とは、どのURLとHTTPメソッドを使い、何を送ると、どのようなレスポンスが返るかという約束です。OpenAPIは、HTTP APIの契約を、人とツールの両方が読み取れる形式で記述するための仕様です。

学習時点のOpenAPI公式仕様を確認し、使用するOpenAPIのバージョンを`openapi`フィールドと回答の両方に記録してください。仕様の最新版と利用するバリデーターが対応する版が同じとは限らないため、選んだ版に対応する検証ツールを使います。

まず公式仕様の構成を確認し、次の最小構成から始めて、問題2で作った二つの操作をYAMLまたはJSONで記述してください。

  title: Task API

- `GET /api/tasks`
- `POST /api/tasks`

最後に、フロントエンド側とAPI側を別々の人やAIが作る場合に、実装前に契約を決める利点と、仕様書が更新されない場合の危険を説明してください。

## 第5章　データベースとデータモデル

この章では、サーバーを再起動してもタスクが残るように、データベースへ保存します。表形式でデータを管理するリレーショナルデータベースを例に、テーブル設計、SQLとORMの使い分け、スキーマ変更とトランザクションを学びます。

### 問題1：利用者とタスクの関係をテーブルで表そう

データベースの構造を表す設計を「データモデル」といいます。リレーショナルデータベースでは、データの種類ごとにテーブルを作り、各データを行、項目を列として表します。

次の条件を持つタスク管理アプリのデータモデルを設計してください。

- 利用者は、一意なID、表示名、メールアドレス、作成日時を持つ
- 同じメールアドレスの利用者を重複登録しない
- タスクは、一意なID、所有者のID、タイトル、完了状態、省略可能な期限、作成日時、更新日時を持つ
- 1人の利用者は複数のタスクを所有できる
- タスクは必ず1人の利用者に所有される

`users`と`tasks`の二つのテーブルについて、列名、データ型、必須か省略可能か、初期値、制約を表にしてください。主キー、外部キー、`NOT NULL`、`UNIQUE`の役割を説明し、テーブル同士の関係を矢印で表したER図も作ってください。ER図は、データの種類とその関係を表す図です。

この問題では、まずPostgreSQLなどの一般的な論理モデルとして型を設計します。問題2でSQLiteに実装するときは、論理上の真偽値や日時がSQLiteやORM上でどの型として保存されるかを別に確認し、違いを記録してください。

最後に、利用者を削除しようとしたとき、所有するタスクの削除も禁止する、タスクも同時に削除する、所有者情報を別の値に置き換えるなどの選択肢を比較してください。タスク管理アプリで自分ならどの方針を選ぶか、データの整合性と利用者への影響を理由にして書いてください。この判断には、サービスの方針によって複数の考え方があります。

`SET NULL`を選ぶ場合は、「タスクは必ず1人に所有される」という現在の要件と矛盾するため、所有者IDを省略可能にするなどの設計変更が必要です。選んだ方針が、必須・省略可能の設計と一致するかも確認してください。

> **ヒント：**「PostgreSQL primary key foreign key official」「PostgreSQL NOT NULL UNIQUE constraints」「データベース ER図 1対多」「foreign key ON DELETE CASCADE RESTRICT SET NULL」というキーワードを使って調べてください。

### 問題2：SQLとORMの両方から、データの保存と取得を理解しよう

SQLは、リレーショナルデータベースに対してデータの作成、取得、変更、削除などを指示する言語です。ORM（Object-Relational Mapping）は、プログラミング言語のオブジェクトや関数を使って、データベースを操作しやすくする道具です。ORMを使っても、実際のデータベースではSQLに相当する処理が行われます。

この教材の標準経路では、ローカルで練習しやすいSQLiteとPrisma ORM v7系を使います。同じ主要バージョン内の安定版を選び、PrismaとSQLiteのバージョンを記録して、Prisma ORM v7に対応する公式ドキュメントに従ってください。別のデータベースやORMで試す場合は発展課題とし、標準経路との操作や生成物の違いを記録します。

第6章で認証を学ぶまでは、サーバー側の設定に固定した練習用利用者IDを、新しいタスクの所有者として使います。APIのリクエスト本文やヘッダーに利用者IDを自由入力させ、そのまま所有者として信用してはいけません。第6章では、この固定IDを検証済みの模擬セッションから得たIDへ置き換えます。

次の順序で実際に操作してください。1〜4と6を必須、5と「実際に生成されたSQLログの確認」を発展課題とします。

1. 問題1の`users`と`tasks`に相当するモデルをORMで定義する
2. 最初のマイグレーションを作成・実行し、生成されたファイルの内容を確認する
3. 2人の利用者と、それぞれが所有する複数のタスクを登録する
4. 指定した1人の利用者に属するタスクだけを取得する
5. 【発展】タスクを1件追加し、完了状態を変更し、最後にそのタスクを削除する
6. 第4章で作ったAPIの配列操作を、ORMを使うデータベース操作へ置き換える

さらに、存在しない利用者IDでタスクを作成しようとし、外部キー制約で拒否されるか確認してください。SQLiteで外部キー制約が有効になる条件を調べ、使用しているORMと接続で実際に有効かを確認します。

「利用者IDを指定してタスクを取得する」処理と「タスクを1件追加する」処理について、ORMのコードと、自分で書いた同等の`SELECT`や`INSERT`のSQLを並べてください。【発展】ORMのクエリログで実際に生成されたSQLも確認し、自分のSQLと同じとは限らない理由を考えます。どちらのSQLでも、値をどのように安全に渡すかを確認してください。利用者の入力をSQL文の文字列へ直接連結する危険性と、パラメーター化されたクエリの役割も調べます。

最後に、SQLを直接書く方法とORMを使う方法を、型の支援、複雑なクエリの分かりやすさ、生成されるSQLの確認、異なるデータベースへの移行という観点から比較してください。どちらかが常に正解ではないことに注意し、自分ならどのように使い分けるかを書いてください。

> **ヒント：**「SQLite official documentation」「Prisma ORM SQLite quickstart official」「ORM SQL 違い」「SQL CRUD SELECT INSERT UPDATE DELETE」「SQL injection parameterized query OWASP」というキーワードを使って調べてください。

### 問題3：マイグレーションとトランザクションで変更の安全性を考えよう

データベースのテーブルや列などの構造を「スキーマ」といいます。スキーマの変更を履歴として記録し、異なる環境に同じ順番で適用する仕組みが「マイグレーション」です。

問題2で作ったデータベースに、タスクの優先度を表す`priority`を追加するとします。既存の行がある状態で必須列を追加すると何が起こり得るかを調べ、次の案を比較してください。

- 最初から必須列として追加する
- 既定値を持つ列として追加する
- まず省略可能な列として追加し、既存行へ値を入れてから必須に変更する

ローカルの練習用データベースで選んだ方法をマイグレーションとして実行し、実行前後のデータと生成されたSQLまたは変更手順を確認します。マイグレーションファイルをレビューせずに実行する危険性や、開発環境のデータベースを作り直す操作を、本番環境で同じ感覚で実行してはいけない理由も説明してください。

次に、「タスクを完了に変更する」と「操作履歴テーブルへ完了操作を記録する」という二つの処理を考えます。操作履歴テーブルには、一意な`id`、対象の`taskId`、操作を表す`action`、操作日時の`createdAt`を持たせ、`taskId`の外部キーとタスク削除時の扱いを設計してください。

複数のデータベース操作を、すべて成功した場合だけ確定し、途中で失敗した場合はすべてを元に戻す仕組みを「トランザクション」といいます。

使用しているORMまたはデータベースのトランザクション機能を使って二つの処理を実行し、正常時の結果を確認してください。その後、二つ目の処理で意図的にエラーを起します。エラーをトランザクション内で握りつぶさず外側へ送出し、ロールバックさせて、タスクの完了状態と操作履歴のどちらも変更されて残っていないことを確認します。確認後は意図的なエラーを元に戻してください。

> **ヒント：**「database migration existing data NOT NULL column」「Prisma Migrate migration history official」「database transaction commit rollback」「PostgreSQL transactions official」「development production database reset danger」というキーワードを使って調べてください。

## 第6章　認証・認可とWebセキュリティ

この章では、利用者が誰かを確かめ、操作できるデータの範囲を制限し、外部から受け取る値や秘密情報を安全に扱う考え方を学びます。セキュリティの確認やテストは、自分で作成したローカル練習環境だけを対象にしてください。他人のWebサイトやAPIに対し、許可なく入力の改変、脆弱性検査、自動化した大量リクエストを行ってはいけません。

### 問題1：認証・セッション・認可は何が違うのか

「認証」は利用者が誰であるかを確かめること、「セッション管理」は認証済みの状態を複数のHTTPリクエストにまたがって管理すること、「認可」は認証された利用者がどのデータや機能を利用できるかを判定することです。

次のタスク管理アプリの流れについて、どこが認証、セッション管理、認可に当たるかを区別してください。

1. 利用者がメールアドレスとパスワードを送信する
2. サーバーが登録情報と比較する
3. ログイン成功後の情報をCookieなどで維持する
4. 次のリクエストで現在の利用者を特定する
5. 表示または変更しようとしているタスクが、その利用者のものか確認する

パスワードを平文、つまり入力された文字列のまま保存してはいけない理由と、パスワードハッシュの役割を調べてください。通常の高速なハッシュ関数ではなく、パスワード用に設計された遅いハッシュまたはKDF（キー導出関数）と、同じパスワードでも異なる結果を作るためのソルトが必要な理由も確認します。暗号化とハッシュが常に同じ意味ではないことにも注意します。学習目的でも独自のハッシュ方式やセッション方式を本番利用するのではなく、信頼できる認証ライブラリを使う利点も説明してください。

さらに、セッション識別子をCookieで保存する場合の`HttpOnly`、`Secure`、`SameSite`、`Path`、`Max-Age`または`Expires`の役割を調べてください。本番のHTTPS環境とローカル開発環境で`Secure`の動作条件がどのように異なるか、`SameSite`はCSRFリスクを減らす一つの対策であって、すべての状況を単独で解決するものではないことも確認します。ログイン、ログイン済みページの表示、ログアウトまでのリクエストとレスポンスの流れを図にし、Cookieがどのタイミングで設定・送信・削除されるかを表してください。

> **ヒント：**「Next.js authentication authorization session management official」「OWASP Authentication Cheat Sheet」「password hashing encryption difference」「Set-Cookie HttpOnly Secure SameSite」「authentication library benefits」というキーワードを使って調べてください。

### 問題2：URLのIDだけを信用せず、タスクの所有者を確認しよう

ログイン済みの利用者Aが、`/api/tasks/task-100`へリクエストを送ったとします。`task-100`が利用者Bのタスクであっても、サーバーがIDだけでデータを取得して返すと、利用者Aは他人のデータを見られてしまいます。このような問題を「オブジェクトレベルの認可の不備」といいます。

次の処理には、どのような問題があるか説明してください。これは概念を示す疑似コードであり、特定のORMでそのまま動くコードとは限りません。

```ts
const task = await database.task.findById(requestedTaskId);
return Response.json(task);
```

現在のセッションから得た`currentUserId`と、URLから受け取った`requestedTaskId`の両方を使い、「指定されたIDで、かつ現在の利用者が所有するタスク」だけを読み取れるように修正してください。取得、変更、削除のすべてで同じ確認が必要な理由も説明します。

この教材では実際のログイン機能を作り込む代わりに、サーバー側だけから利用するテスト専用の`getTestSession()`関数を作ります。この関数は、テストごとに利用者A、利用者B、または未ログインに相当する値を返します。ブラウザーから自由に送れるCookie、ヘッダー、リクエスト本文の利用者IDをそのまま返す実装にはしないでください。本番用の認証ではないことをコメントと回答に明記し、実運用では認証ライブラリが検証したセッションから`currentUserId`を得る必要があることを説明します。

ローカル練習環境に利用者AとBのテストデータを用意し、次のケースを確認してください。本物の利用者データは使わないでください。

- AがAのタスクを取得できる
- AがBのタスクIDを指定しても、取得できない
- AがBのタスクを変更または削除できない
- ログインしていない利用者は保護されたAPIを利用できない

画面から編集ボタンを隠すだけでは不十分な理由、推測しにくいIDを使っても所有者確認を省略できない理由、認可されないデータに`403 Forbidden`と`404 Not Found`のどちらを返すかという判断についても、情報漏えいとAPI利用者の分かりやすさの両面から考えてください。

> **ヒント：**「OWASP API broken object level authorization」「API object ownership authorization check」「Next.js data access layer authorization」「401 403 404 security difference」「IDOR BOLA 違い」というキーワードを使って調べてください。

### 問題3：タスク管理アプリのセキュリティレビューをしよう

セキュリティは、特定の対策を1回追加すれば完成するものではありません。ブラウザー、API、サーバー、データベースの各境界で、外部から受け取る値と、外部へ送る値を確認する必要があります。

次のタスク管理アプリの状況について、起こり得る問題、問題が起きる理由、確認する場所、対策の方針を表にしてください。

1. Reactの通常の`{title}`で文字列として表示せず、`dangerouslySetInnerHTML`などを使って、未検証の利用者入力をHTMLとして解釈させる
2. SQLを組み立てるときに、利用者が入力したタイトルをSQL文の文字列へ直接連結する
3. データベース接続情報を`NEXT_PUBLIC_DATABASE_URL`という名前で保存する
4. ログイン状態のCookieに`HttpOnly`、`Secure`、`SameSite`の設定がない
5. Cookieで認証されるログイン中のブラウザが、別のサイトから単純なフォームPOSTなどで、意図しない状態変更リクエストを送らされる
6. CORSの問題を解決するために、受け取った任意の`Origin`を`Access-Control-Allow-Origin`へそのまま返し、Cookieなどの認証情報も許可する

XSS、SQLインジェクション、秘密情報の漏えい、Cookieの不適切な設定、CSRF、CORSについて、それぞれが何かを初心者向けに説明してください。Reactの通常の文字列表示で行われるエスケープと、未検証のHTMLを意図的に解釈させる場合を区別します。

CORSについては、`Access-Control-Allow-Origin: *`とCookieを含むリクエストの制約、任意の`Origin`を反射して認証情報も許可する設定の危険性、プリフライトが必要なリクエストと単純なリクエストの違いを調べてください。CORSはブラウザーが異なるオリジン間のレスポンス読み取りを制御する仕組みであり、認証、認可、CSRF対策の代わりにはならないことも確認します。

各ケースに対する対策をすぐ調べる前に、まず自分で「どの境界で、何を信用しすぎているか」を予想してください。その後にOWASPやNext.jsの公式資料と比較し、入力検証だけで他の対策を置き換えられるかも判断してください。

最後に、第4章で作成したAPI、第5章で作成したデータベース操作、第6章で設計した認証・認可を対象に、自分がコードやAIの提案を確認するためのセキュリティチェックリストを10項目以内で作ってください。各項目には、「何を見るか」だけでなく、「どのような結果なら問題がないと判断するか」も含めてください。

> **ヒント：**「OWASP Input Validation Cheat Sheet」「OWASP XSS Prevention Cheat Sheet」「OWASP SQL Injection Prevention Cheat Sheet」「Next.js data security environment variables」「OWASP CSRF Prevention CORS」というキーワードを使って調べてください。

## 第7章　テストと品質保証

この章では、第1〜6章で作ったタスク管理アプリが期待どおりに動き続けることを、再現できる方法で確かめます。テストは「バグが絶対にない」と証明するものではなく、決めた条件で期待する結果になるかを繰り返し確認し、変更による不具合の再発を見つけやすくする仕組みです。

### 問題1：どの機能を、どの種類のテストで確かめるか設計しよう

テストには、関数などの小さな単位を確かめる「単体テスト」、コンポーネントや複数の処理の組み合わせを確かめる「コンポーネントテスト」や「結合テスト」、ブラウザーを操作して利用者の一連の流れを確かめる「E2Eテスト」などがあります。TypeScriptの型検査や静的解析も、実行前に問題を見つける重要な確認ですが、実行時の振る舞いを確かめるテストとは役割が異なります。

まず、単体テスト、コンポーネントテスト、結合テスト、E2Eテスト、手動確認について、確認できる範囲、実行速度、失敗時の原因の探しやすさ、実行環境の準備という観点から比較してください。名称や範囲は資料やチームによって多少異なるため、参考にした資料での定義も書きます。

次に、タスク管理アプリの以下の対象について、「主にどの方法で確かめるか」「その方法を選ぶ理由」「失敗したときに利用者へどのような影響があるか」を表にしてください。一つの機能を複数の種類で確かめても構いませんが、同じ内容をすべての層で重複させる必要があるかも考えます。

- タスク名から前後の空白を除き、空文字や最大文字数超過を拒否する関数
- タスク入力フォームの表示、入力、エラーメッセージ
- Route Handler、データベース、レスポンスを組み合わせたタスク作成API
- ログイン中の利用者が自分のタスクだけを変更できる認可
- タスクを作成し、完了にして、一覧で確認する利用者の流れ

各対象について、正常な場合だけでなく、境界値、入力間違い、未ログイン、他人のデータ、通信失敗などから重要なケースを選んでください。すべての組み合わせを無理に列挙するのではなく、危険度と起こりやすさをもとに優先順位を付けます。

最後に、選んだケースを「前提条件」「操作または入力」「期待する結果」の三つに分けて書き、AIが作ったテストをレビューするときの基準を5項目以内で作ってください。実装の内部構造だけを確認していないか、失敗させると本当にテストが失敗するか、偶然通る条件になっていないかも判断基準に含めます。

> **ヒント：**「Next.js testing types official」「unit integration end-to-end test difference」「test case boundary value」「Given When Then test」「AI generated tests review」というキーワードを使って調べてください。

### 問題2：入力検証とフォームの自動テストを書こう

第4章で作ったタスク名の入力検証を、副作用を持たない関数として切り出します。「副作用」とは、引数から戻り値を計算する以外に、外部のデータを書き換えたり通信したりする影響のことです。切り出した関数とタスク入力フォームを対象に、使用しているNext.js、React、テストツールのバージョンを記録し、対応する公式手順でテスト環境を準備してください。

この問題では、単体テスト用のツールとしてVitestまたはJest、コンポーネントの操作にはTesting Libraryなど、現在の構成に対応する組み合わせを選びます。別の道具を選んでも構いませんが、なぜその構成で動くのかを説明してください。`async`なServer Componentはテストツールが十分に対応していない場合があるため、学習時点のNext.js公式資料を確認し、対象外にした部分はE2Eテストなど別の確認方法を決めます。

入力検証関数について、少なくとも次のケースを実装してください。最大文字数は自分のAPIで決めた値を使います。

- 通常のタスク名を受け入れる
- 空白文字だけの値、または空文字を拒否する
- 最大文字数と同じ長さを受け入れる
- 最大文字数を1文字超えた値を拒否する
- 文字列以外の値を拒否する

JavaScriptの`length`で数える場合と、Unicodeのコードポイントや利用者が画面上で一文字と感じる単位で数える場合では、絵文字などの数え方が異なることも調べてください。今回採用する文字数の数え方を決め、画面、API、テストで同じ基準になるようにします。

次に、タスク入力フォームについて、利用者が入力して送信したときの表示を確かめます。要素を探すときは、壊れやすいCSSクラス名だけに依存せず、利用者や支援技術が認識するラベル、ボタン名、役割を優先してください。正常な入力では送信処理が呼ばれ、不正な入力では理解できるエラーメッセージが表示されることを確認します。送信処理は本物のAPIへ接続せず、テスト用の関数へ置き換えて、呼び出された値を検証してください。

一つのテストで期待値を意図的に誤った値へ変え、テストが失敗することと、失敗表示から原因をたどれることを確認したあと、元へ戻してください。最後に、行カバレッジなどの数値が高くても重要な動作を見落とす場合を一例挙げ、テスト件数やカバレッジだけで品質を判断できない理由を書いてください。

> **ヒント：**「Next.js Vitest guide official」「Next.js Jest guide official」「Testing Library queries priority」「test boundary values」「test coverage limitations」というキーワードを使って調べてください。

### 問題3：ブラウザーを使うE2Eテストで主要な流れを確かめよう

E2Eテストでは、実際のブラウザーに近い環境で画面を操作し、フロントエンド、API、データベースなどを通る利用者の流れをまとめて確認します。この問題ではPlaywrightを例にします。別のE2Eテストツールを使う場合は、同じ確認内容になるように読み替えてください。

本番データや開発中の大切なデータベースを使わず、E2Eテスト専用の環境とテストデータを用意してください。テストの実行順序に依存しないように、各テストの開始状態をそろえ、作成したデータを識別できるようにします。テスト専用の認証切り替えを作る場合は、本番ビルドで利用できない構成にし、本番の認証を迂回する入口として残らないことを確認してください。

次の利用者の流れから二つ以上を選び、E2Eテストを書いてください。最初の二つを必須とし、認可の確認は発展課題とします。

1. タスクを作成し、一覧に表示され、ページを再読み込みしても残っている
2. 自分のタスクを完了状態へ変更し、その表示を確認する
3. 【発展】未ログインの利用者が保護されたページやAPIを利用できない
4. 【発展】利用者Aが利用者Bのタスクを変更できない

要素の選択には、可能な限り`getByRole`や`getByLabel`など、利用者から見える意味を使います。固定時間の待機を何度も追加するのではなく、対象が操作可能になるまでの自動待機と、期待する表示を再試行するアサーションを使ってください。失敗時にスクリーンショット、トレース、ログなどのどれを残すと原因を調べやすいかも設定します。架空のテストデータだけを使い、成果物へCookie、セッション識別子、入力した秘密情報や個人情報を残さないようにしてください。CIへ成果物を保存する場合は、閲覧できる人、保存期間、削除条件も確認します。

同じテストを複数回実行し、毎回同じ結果になるか確認してください。ときどき成功し、ときどき失敗するテストを「不安定なテスト」と呼びます。不安定になった場合は、待ち時間を増やす前に、共有データ、実行順序、曖昧な要素の選択、非同期処理の完了条件を調べます。最後に、単体テストだけでは見つけにくかった問題と、E2Eテストだけでは原因を特定しにくかった問題を一つずつ説明してください。

> **ヒント：**「Next.js Playwright guide official」「Playwright best practices locators」「Playwright auto waiting assertions」「E2E test isolation test data」「Playwright trace screenshot failure」というキーワードを使って調べてください。

## 第8章　パフォーマンスとアクセシビリティ

この章では、機能が動くだけでなく、待ち時間が短く、画面のずれが少なく、さまざまな操作方法や利用環境でも使いやすいWebアプリを目指します。推測だけで最適化せず測定結果を残し、アクセシビリティは自動検査と人による操作確認を組み合わせます。

### 問題1：表示の速さと安定性を測り、改善対象を決めよう

Webのパフォーマンスは、サーバーの処理時間やファイルサイズだけでなく、利用者が主要な内容を見られるまでの時間、操作への反応、読み込み中の画面のずれなどから考えます。Core Web Vitalsの`LCP`、`INP`、`CLS`がそれぞれどのような利用体験を表すか、学習時点の公式資料で調べてください。指標の基準値は更新される可能性があるため、参照日と情報源も記録します。

タスク一覧ページを本番用にビルドし、本番に近いローカル実行で測定してください。開発モードの追加処理やブラウザー拡張機能が結果へ影響する可能性があるため、測定条件をそろえます。Lighthouse、ブラウザーのPerformanceパネル、Networkパネルなどから説明できる道具を選び、次を記録してください。

- 使用したアプリとブラウザー、バージョン
- 画面幅、端末の模擬設定、ネットワークやCPUの制限
- 測定したページと操作
- 複数回測定した結果と、代表値の選び方
- LCP、INP、CLSまたは代替となる観測結果
- 読み込みに時間がかかったリソースと、画面が変化したタイミング

Lighthouseのような制御された環境で測る「ラボデータ」と、実際の利用者の環境から集める「フィールドデータ」の違いも説明してください。ローカル練習ではラボデータを使いますが、1回の点数だけで全利用者の体験を断定できない理由を考えます。

測定結果をもとに、改善候補を三つ挙げ、「利用者への影響」「実装の手間」「測定で得た根拠」で優先順位を付けてください。まだ測定していない思い込みと、記録から確認できた事実を分けて書き、最初に改善する一つを選びます。

> **ヒント：**「web.dev Core Web Vitals LCP INP CLS」「Next.js production checklist performance」「Chrome DevTools Performance Network」「Lighthouse lab data field data」「performance measurement median multiple runs」というキーワードを使って調べてください。

### 問題2：画像・JavaScript・データ取得の負荷を見直そう

問題1で記録した結果を使い、タスク管理アプリの負荷を改善します。Next.jsが提供する画像とフォントの最適化、Client Componentとしてブラウザーへ送るJavaScriptの範囲、必要になるまで処理を読み込まない遅延読み込み、データのキャッシュについて、使用中のNext.jsバージョンの公式資料を確認してください。フレームワークが自動で行う最適化と、自分で設計する必要がある部分を区別します。

次のうち、測定結果と関係する二つ以上を選び、変更前と変更後を同じ条件で比較してください。

- 大きな画像を適切な寸法・形式・読み込み優先度で配信する
- Webフォントの読み込み方を見直し、文字表示やレイアウトのずれを減らす
- 大きなライブラリや、最初の画面で不要な機能を遅延読み込みする
- Server ComponentとClient Componentの境界を見直し、ブラウザーへ送るJavaScriptを減らす
- 同じデータを不必要に何度も取得していないか確認する

変更ごとに、変更したファイル、転送量やリクエスト数がどう変わったか、LCPやCLSなどがどう変わったか、機能上の欠点や複雑さが増えなかったかを表にします。ブラウザーから送ったHTTP通信はNetworkパネル、Server Component内部の取得やデータベース問い合わせは開発用ログ、ORMのクエリログ、トレースなど、処理が行われる層に合う方法で確認してください。数値が改善しなかった場合も隠さず、仮説が違ったのか、測定のばらつきなのかを考えます。一度にすべてを変更せず、どの変更が結果へ影響したか分かる単位で確認してください。

キャッシュを試す場合は、公開してよい共通データと、利用者ごとに異なるタスクや認証済みレスポンスを区別してください。個人データを共有キャッシュへ誤って保存すると何が起こるかを説明し、キャッシュキー、再検証、データ更新後の無効化をどのように扱うか設計します。速さのためにデータの正しさや認可を失わないことを確認してください。

最後に、AIが提案した最適化を採用する条件をまとめます。「速そう」という説明だけでなく、変更前後の測定、機能テスト、コードの複雑さ、利用中のフレームワークで推奨される方法かどうかを判断基準にしてください。

> **ヒント：**「Next.js Image optimization official」「Next.js Font optimization official」「Next.js lazy loading dynamic import」「Next.js Server Client Components bundle size」「Next.js caching user-specific data security」というキーワードを使って調べてください。

### 問題3：キーボードと支援技術でも使える画面へ改善しよう

アクセシビリティとは、障害の有無、使用する端末、入力方法などが異なっても、できるだけ多くの人が情報や機能を利用できるようにする考え方です。WCAGはWebアクセシビリティの達成基準をまとめた国際的なガイドラインです。この問題では、学習時点のWCAG 2.2とW3Cの解説を参照し、特定の国の法令に適合したと自己判断するのではなく、タスク管理アプリの具体的な問題を見つけて改善します。

タスク作成フォームとタスク一覧を、まずマウスを使わずキーボードだけで操作してください。次の項目を確認し、成功条件、実際の結果、修正内容を表にします。

- 見出しとランドマークが内容の構造を表している
- 入力欄に、見た目だけでなくコード上も関連付いたラベルがある
- タブ移動の順序が自然で、現在のフォーカス位置が見える
- ボタンやリンクをキーボードで操作でき、見た目だけで役割を決めていない
- 入力エラーの場所と直し方が、色だけに頼らず伝わる
- タスク追加やエラーなどの重要な変化が、画面を見ていない利用者にも伝わる
- 文字と背景に読み取れるコントラストがある

HTML標準の`button`を使う場合と、`div`にクリック処理やARIA属性を追加してボタンのようにする場合を比較してください。ARIAはHTMLの意味を補う仕組みですが、適切なHTML要素の動作を自動的にすべて再現するものではありません。自分ならどちらを選ぶか、キーボード操作、役割、状態、保守の観点から理由を書きます。

ブラウザーのアクセシビリティツリー、Lighthouse、axeなどの自動検査から利用できるものを一つ使い、検出された問題を修正してください。その後にキーボードで再確認します。自動検査で問題が0件でも、分かりにくいラベル、自然でないフォーカス移動、操作後の通知などを見落とす可能性がある理由も説明してください。

【発展】利用できる場合は、macOSのVoiceOver、WindowsのNVDAなどのスクリーンリーダーを使い、入力欄のラベル、入力エラー、タスク追加後の通知のうち一つ以上が伝わるか確認してください。操作した環境と、読み上げられた内容、期待と異なった点を記録します。

最後に、今回確認した内容から、今後AIへ画面実装を依頼するときに最初から伝えるアクセシビリティ要件を8項目以内で作ってください。各項目には、実装方法だけでなく、完成後に人がどう操作して確認するかも含めます。

> **ヒント：**「W3C WCAG 2.2 Quick Reference」「WAI form labels tutorial」「WAI keyboard accessible」「semantic HTML button ARIA」「accessibility automated testing limitations」というキーワードを使って調べてください。

## 第9章　デプロイ・CI/CD・監視と運用

この章では、ローカルで動くアプリを公開できる形へ準備し、変更を安全に届け、公開後の異常へ気づいて対処する流れを学びます。実際の有料サービスへの公開は必須ではありません。公開する場合は練習用アカウントとデータだけを使い、料金、公開範囲、秘密情報の保存先を事前に確認してください。

### 問題1：タスク管理アプリに合うデプロイ方法を選ぼう

「デプロイ」とは、アプリを利用できる環境へ配置し、必要な設定をそろえて起動することです。開発用サーバー、本番用ビルド、本番用サーバーの役割の違いを調べ、使用しているNext.jsバージョンでのコマンドと生成物を確認してください。

まず、Next.jsの実行・出力方式として、Node.jsサーバー、コンテナー、静的エクスポートを調べて比較してください。その後、選んだ方式を配置できるホスティングサービスを一つ以上調べます。実行方式と配置先を別の選択として整理し、次の観点で比較表を作ってください。

- ビルド時に処理できるServer Componentと、リクエスト時のCookieや動的なRequestを必要とする処理への対応
- `POST`など状態を変更するRoute Handlerや、認証など必要なNext.js機能への対応
- データベースへの接続とマイグレーションを実行する場所
- 環境変数と秘密情報の管理
- 【発展】複数インスタンスで動く場合のメモリー、ファイル、キャッシュの共有
- 更新、ロールバック、ログ確認のしやすさ
- 料金や、利用量が増えた場合の制限

第4〜6章で作ったタスク管理アプリは、サーバー側のAPI、データベース、認証・認可を使います。静的エクスポートでもビルド時に実行できる処理がある一方、リクエストごとのCookie、動的なRequest、`POST`などは同じ方法で提供できないことを、使用中のNext.js公式資料で確認してください。不足する機能を別のAPIやサービスへ移す案も含めて、自分ならどの方式と配置先を選ぶか理由を書きます。ホスティングサービスによって対応機能が異なるため、一般的な説明だけでなく、選んだサービスの公式資料も確認してください。

この問題では、方式の比較、ローカルでの本番用ビルドと本番用サーバーの確認、チェックリスト作成を必須とし、外部ホスティングへの実デプロイは発展課題とします。ビルドエラー、必要な環境変数の不足、データベース接続失敗をそれぞれどの段階で検出できるか調べてください。開発、テスト、本番でデータベースと秘密情報を分け、`.env`ファイルをリポジトリへ含めない理由も説明します。ブラウザーへ公開される環境変数とサーバーだけで使う環境変数を区別してください。

最後に、公開前、公開直後、問題発生時のチェックリストを作ってください。データベースのバックアップとマイグレーション順序、ヘルスチェック、主要なE2Eテスト、秘密情報、監視、以前の版へ戻す条件を含めます。ロールバックしてもデータベース変更を単純には元へ戻せない場合があることも考えてください。

> **ヒント：**「Next.js deploying official Node Docker static export」「Next.js production checklist official」「Next.js environment variables official」「database migration deployment rollback」「deployment health check rollback plan」というキーワードを使って調べてください。

### 問題2：CIでテストし、安全に変更を届ける流れを作ろう

CI（継続的インテグレーション）は、コードの変更を共有するたびに、型検査、静的解析、テスト、ビルドなどを自動で実行して、統合前に問題を見つけやすくする仕組みです。CDは、確認済みの変更を配布できる状態にする「継続的デリバリー」または本番まで自動で反映する「継続的デプロイ」を指すことがあります。どちらを意味しているか、使う場面で確認する必要があります。

GitHub ActionsなどのCIサービスを一つ選び、Pull Requestまたは作業ブランチへの変更で、次の処理を実行するワークフロー設定を作ってください。設定ファイルの作成と、同じコマンドがローカルで成功する確認を必須とし、外部CIでの実行は発展課題とします。外部CIを使う場合は、練習用または非公開リポジトリを使い、実行時間や料金の上限、ログと成果物の公開範囲も先に確認してください。利用するAction、Node.js、パッケージ管理ツールのバージョンは公式資料で確認し、選んだ値を記録します。

1. リポジトリのコードを取得する
2. プロジェクトで指定したNode.jsを準備する
3. ロックファイルに従って依存関係を再現可能な方法で導入する
4. 型検査または静的解析を実行する
5. 単体・結合テストを実行する
6. 本番用ビルドを実行する
7. 必要に応じてE2Eテストの結果や失敗時の成果物を保存する

まずローカルで同じ処理が成功することを確認します。【発展】外部CIを実行する場合は、正常なワークフローの成功後、テストの期待値または型を意図的に壊し、CIが失敗を検出することを確認してから元へ戻してください。CIの失敗だけで自動的にマージが禁止されるとは限りません。ブランチ保護や必須ステータスチェックに設定すると、失敗中のマージを防げる理由も説明します。どの処理で失敗したか、ログから原因を特定できるかも記録してください。ローカルでは成功してCIでは失敗する場合に、Node.jsの版、環境変数、OS、時刻、テストデータ、依存関係の違いをどの順に調べるか説明します。

CI用の権限と秘密情報は必要最小限にします。秘密情報をワークフローファイルへ直接書かず、ログへ表示しないこと、Pull Requestなど信頼できない入力をシェルコマンドへ直接埋め込まないこと、第三者のActionをどの版で固定し、どの権限を与えるかを確認してください。テスト用データベースの認証情報と本番用の認証情報も分けます。

最後に、テスト成功後すぐ本番へ自動デプロイする案と、ステージング環境や人の承認を挟む案を比較してください。このタスク管理アプリで採用する流れを図にし、誰が、何を確認し、どの条件で中止またはロールバックするかを書きます。この判断には、利用者数、変更の危険度、チーム体制によって複数の考え方があります。

> **ヒント：**「GitHub Actions Node.js build test official」「continuous integration delivery deployment difference」「npm ci lockfile CI」「GitHub Actions secure use secrets permissions」「deployment environment required reviewers」というキーワードを使って調べてください。

### 問題3：ログ・メトリクス・トレースから障害へ対応しよう

公開後のアプリの状態を外部から理解し、原因を調べられるようにする考え方を「可観測性」といいます。代表的な情報には、個々の出来事を記録するログ、件数や時間を集計するメトリクス、一つのリクエストが複数の処理を通る流れを追うトレースがあります。それぞれが答えやすい質問と、保存量や調査方法の違いを整理してください。

タスク作成APIを対象に、次の情報を設計します。外部の監視サービスの契約は必須ではなく、まずローカル環境の構造化ログと簡単な集計で確認して構いません。構造化ログは、後から項目ごとに検索・集計できるように、JSONなど一定の形で出力するログです。ただし、ログを数回集計する練習と、カウンターやヒストグラムなどを継続的に収集する本格的なメトリクス基盤は同じではないことを区別してください。

- ログ：時刻、重要度、イベント名、リクエストを関連付けるID、処理結果、HTTPステータス、処理時間
- メトリクス：リクエスト数、エラー率、応答時間、データベース失敗数
- 【発展】トレース：画面またはAPIから、認可、データベース処理、レスポンスまでの区間

パスワード、Cookie、セッション識別子、APIキー、データベース接続文字列、必要のないリクエスト本文や個人情報をログへ残してはいけません。利用者IDやURLをメトリクスのラベルへそのまま入れると、種類の組み合わせが増え続け、保存量や費用が急増する可能性も調べてください。どの情報を記録し、除外・伏字化し、何日保持するかを表にします。

ローカル練習環境で、正常なタスク作成、入力不備による`4xx`、意図的なデータベース失敗による`5xx`、意図的に遅くした処理を一度ずつ発生させます。確認後は意図的な失敗と遅延を元へ戻してください。ログと集計結果から、それぞれの時刻、リクエスト、失敗箇所、処理時間を区別できるか確認します。入力間違いによる`4xx`とサーバー障害による`5xx`を同じ重大度で通知すると何が起こるかも考え、一定時間のエラー率や遅延を使った通知条件を仮に設計してください。4回の練習結果だけで実運用の閾値を確定せず、想定負荷、通常時の値、許容する影響、誤通知の回数をもとに運用しながら見直す方法も説明します。

最後に、「タスクを作成できない」という障害を想定して、検知、影響範囲の確認、直前の変更の確認、被害を抑える操作、ロールバックまたは修正、復旧確認、利用者への連絡、再発防止までの手順書を作ってください。最初から原因を一つに決めつけず、どのログ、メトリクス、トレース、デプロイ履歴、データベース状態をどの順番で確認するかを書きます。

> **ヒント：**「OpenTelemetry observability logs metrics traces」「OWASP Logging Cheat Sheet sensitive data」「structured logging request ID」「HTTP error rate latency alert」「incident response runbook rollback postmortem」というキーワードを使って調べてください。
