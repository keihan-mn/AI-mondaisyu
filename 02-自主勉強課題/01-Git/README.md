# Git初心者向け学習問題

この教材は、Gitを使ったことがない初心者が、自分で情報を調べ、具体例や自分の意見を文章にまとめるための学習問題です。

## 回答するときの共通ルール

各問題について、次の内容を含めて回答してください。

1. 調べて分かったこと
2. 初心者にも伝わる、自分の言葉での説明
3. 自分で考えた具体例
4. 自分の意見や判断と、その理由
5. 参考にした情報源

## 第1章　Gitの基本知識

### 問題1：Gitは何のために使うのか

Gitとは、何を記録し、どのような問題を解決するための道具でしょうか。「バージョン管理」の意味を調べてください。

そのうえで、ファイルを「完成版」「完成版2」「最終版」のように名前を変えて保存する方法と、Gitを使って変更履歴を管理する方法を比較してください。

Gitを使わずにプログラムを開発した場合に起こりそうな問題について、具体例を挙げて説明してください。

> **ヒント：**「Git バージョン管理とは」「Git 変更履歴」「Gitを使うメリット」というキーワードを使って調べてください。

### 問題2：変更をコミットするまでに何をするのか

Gitでは、ファイルを変更しただけでは、その変更がGitの履歴として記録されたことにはなりません。

ファイルを変更してから、その変更を「コミット」として記録するまでの基本的な流れを調べてください。次の3つの段階がそれぞれ何を意味するのか説明してください。

1. ファイルを変更する
2. 現在の変更状態を確認し、記録する変更を選ぶ
3. 選んだ変更をコミットとして記録する

また、通常の上書き保存とGitのコミットには、どのような違いがあるか説明してください。

最後に、AIにコードの変更を依頼する前に一度コミットしておくと、どのような利点があるか考えてください。

> **ヒント：**「Git 作業の流れ」「git status」「git add」「git commit」「ステージング」というキーワードを使って調べてください。

### 問題3：GitとGitHubは何が違うのか

GitとGitHubは、それぞれ何をするためのものでしょうか。両者の違いを調べ、GitはGitHubがなくても使えるのか説明してください。

また、次の操作にはどのような違いがあるか調べてください。

- 自分のパソコン上でコミットする
- GitHubへ変更内容を送信する

自分一人でバイブコーディングをする場合でもGitHubを利用する利点と、コードを公開・保存するときの注意点をまとめてください。

> **ヒント：**「Git GitHub 違い」「ローカルリポジトリ」「リモートリポジトリ」「git push」「GitHub APIキー 公開」というキーワードを使って調べてください。

## 第2章　ブランチに関して

この章では、次の用語を使用します。

- `main`：開発の基準となる、本線のブランチに一般的に使われる名前
- 作業ブランチ：新機能の追加や不具合の修正など、特定の作業を行うために本線から分けて作るブランチ

### 問題1：ブランチはなぜ必要なのか

Gitにおける「ブランチ」とは何かを調べてください。

AIに新しい機能を作らせる場合を例に、次の2つの進め方を比較してください。

- `main`上で直接コードを変更する
- `main`から作業ブランチを作り、そのブランチ上でコードを変更する

AIの変更が失敗した場合や、期待した結果にならなかった場合、どちらが対処しやすいでしょうか。理由とともに説明してください。

> **ヒント：**「Git ブランチとは」「mainブランチ」「作業ブランチ」「Git ブランチ メリット」というキーワードを使って調べてください。

### 問題2：ブランチを作ってから統合するまでに何をするのか

新しい機能を追加するために、作業ブランチを作ってから、その変更を`main`へ統合するまでの基本的な流れを調べてください。

次の操作を、実際に行う順番に並べて説明してください。

- 現在使用しているブランチを確認する
- `main`から新しい作業ブランチを作る
- 使用するブランチを切り替える
- ファイルを変更する
- 変更内容を確認する
- 変更をコミットする
- 作業ブランチの変更を`main`へ統合する

また、現在使用しているブランチを確認せずに作業を始めると、どのような問題が起こるか考えてください。

> **ヒント：**「git branch」「git switch」「Git 現在のブランチ 確認」「ブランチ コミット マージ 流れ」というキーワードを使って調べてください。

### 問題3：どのようなときに作業ブランチを作るべきか

次の作業を行う場合、新しい作業ブランチを作るべきか、それとも`main`上で作業してもよいかを判断してください。

- 画面上の小さな誤字を修正する
- ログイン機能を追加する
- AIが提案した大規模な変更を試す
- 原因の分からない不具合を調査する
- 複数のファイルにまたがるデザイン変更を行う

この問いに一つの正解はありません。次の観点から、それぞれの判断理由を説明してください。

- 変更の大きさ
- 失敗した場合の影響
- 元に戻しやすいか
- 他の作業と分ける必要があるか
- AIの変更を安全に試せるか

> **ヒント：**「Git ブランチ 使い分け」「feature branch」「ブランチを切る タイミング」「Git AI 開発 ブランチ」というキーワードを使って調べてください。

## 第3章　マージに関して

### 問題1：マージとはどのような操作か

Gitにおける「マージ」とは、あるブランチの変更を別のブランチへ取り込む操作です。

「ログイン機能を作るための作業ブランチ」を例に、次の内容を説明してください。

1. どのブランチでログイン機能を作るのか
2. どのブランチの変更を、どのブランチへ取り込むのか
3. マージした後、`main`はどのような状態になるのか

また、マージすることと、GitHubへ変更を送信することは同じ操作なのか調べてください。

> **ヒント：**「Git mergeとは」「ブランチをmainにマージ」「マージ 取り込む方向」「merge push 違い」というキーワードを使って調べてください。

### 問題2：通常の変更をマージする前に何を確認するべきか

自分で作成した作業ブランチを`main`へマージする前に、確認すべきことを5つ挙げてチェックリストを作ってください。

チェックリストには、次のような観点を含めてください。

- 予定していた変更だけが含まれているか
- プログラムが正常に動くか
- 既存の機能が壊れていないか
- 必要な変更がコミットされているか
- `main`へ取り込んでも問題がない状態か

それぞれについて、「何を確認するか」だけでなく、「確認しなかった場合に何が起こり得るか」も説明してください。

最後に、5つのうち最も重要だと思う確認項目を一つ選び、その理由を書いてください。

> **ヒント：**「Git マージ前 確認」「git status」「git diff」「Git テスト マージ前」「コミット漏れ 確認」というキーワードを使って調べてください。

### 問題3：AIが作った変更をマージしてよいか

AIに一つの機能追加を依頼したところ、予想より多くのファイルが変更されました。画面上では、依頼した機能が正常に動いているように見えます。

この変更を、そのまま`main`へマージしてよいでしょうか。次の観点から、AIが作った変更に特有の危険を調べてください。

- 依頼と関係のないファイルが変更されていないか
- 既存の機能に影響がないか
- セキュリティ上の問題がないか
- 不要なライブラリが追加されていないか
- パスワードやAPIキーが含まれていないか
- 内容を説明できないコードが追加されていないか

最終的に、どのような条件を満たせばマージしてよいと判断するか、自分なりの基準をまとめてください。

> **ヒント：**「AI生成コード レビュー」「Git 変更ファイル 確認」「依存関係 セキュリティ」「APIキー Git コミット」「コードレビュー チェック項目」というキーワードを使って調べてください。

## 第4章　コンフリクトに関して

### 問題1：コンフリクトはなぜ発生するのか

Gitにおける「コンフリクト」とは、Gitが複数の変更を自動では一つに決められない状態です。

次の2つの場合を比較してください。

- 同じファイルの離れた場所を、別々のブランチで変更した場合
- 同じファイルの同じ行付近を、別々のブランチで異なる内容に変更した場合

同じファイルを編集しても、必ずコンフリクトするとは限りません。どのような場合にGitが自動で変更を統合でき、どのような場合に人間の判断が必要になるのか説明してください。

> **ヒント：**「Git コンフリクト 原因」「同じファイル コンフリクト」「Git 同じ行 変更」「Git 自動マージ」というキーワードを使って調べてください。

### 問題2：コンフリクトをどのように解決するのか

コンフリクトが発生したファイルには、Gitが判断できなかった変更箇所を示す記号が表示されます。その記号が何を表しているのか調べてください。

また、コンフリクトの解決方法は「どちらか一方を選ぶ」だけではありません。次の3つの方法について、どのような場合に選ぶか考えてください。

- 一方の変更だけを残す
- 両方の変更を組み合わせる
- 両方を参考にして、新しい内容へ書き直す

コンフリクトを示す記号を削除しただけでは、解決が完了したとはいえないのはなぜでしょうか。解決後に必要な確認も説明してください。

> **ヒント：**「Git コンフリクト 解決」「コンフリクトマーカー」「`<<<<<<<` `=======` `>>>>>>>`」「Git conflict both changes」「コンフリクト解決後 テスト」というキーワードを使って調べてください。

### 問題3：コンフリクトを減らすにはどうすればよいか

コンフリクトは、必ず避けなければならない失敗なのでしょうか。それとも、複数の変更を統合するときに起こり得る通常の出来事なのでしょうか。

次の2つの場合に分けて、コンフリクトを減らすためのルールを考えてください。

- 一人でAIと一緒に開発する場合
- 複数人で開発する場合

変更を小さく分ける、こまめにコミットする、作業範囲を分ける、変更前に最新の状態を確認するといった方法を調べ、自分が特に重要だと思うルールと、その理由を説明してください。

> **ヒント：**「Git コンフリクト 防ぐ」「小さくコミット」「Git 最新状態 取り込む」「チーム開発 作業範囲」「AIコーディング コンフリクト」というキーワードを使って調べてください。

## 第5章　Gitを使った基本的な作業の流れ

この章では、第1章の問題2で学んだ全体像をもとに、ファイルを変更してからコミットするまでの操作を、一つの流れとして詳しく学びます。

### 問題1：3つの場所はどのようにつながっているのか

Gitでは、同じファイルの状態が「作業ディレクトリ」「ステージングエリア」「リポジトリ」という3つの場所にそれぞれ記録されます。それぞれがどのような場所なのかを、自分の言葉で説明してください。

次の操作を行うと、変更がどの場所からどの場所へ進むのかも説明してください。

- ファイルを編集して保存する
- `git add`を実行する
- `git commit`を実行する

3つの場所を「机の上」「提出用の箱」「保管庫」など身近なものにたとえ、初めてGitを使う人にも伝わる具体例を作ってください。ただし、ファイルそのものが消えて別の場所へ移るのではなく、その時点の状態が記録されることも説明してください。

> **ヒント：**「Git 作業ディレクトリ」「Git ステージングエリア」「Git リポジトリ 3つの領域」「git add commit 流れ」というキーワードを使って調べてください。

### 問題2：変更してからコミットするまでに何を確認するのか

Webページの見出しを修正する作業を例に、ファイルを編集してからコミットするまでの手順を組み立ててください。次のコマンドを実行する順番と、それぞれの目的を説明してください。

- `git status`
- `git diff`
- `git add`
- `git diff --staged`
- `git commit`

同じコマンドを必要に応じて複数回使っても構いません。各段階でどのような表示を確認できれば次へ進んでよいかも考えてください。`git add`した後は通常の`git diff`に何も表示されなくても、コミット対象がないとは限りません。その理由も調べてください。

最後に、コミット直前に`git status`と`git diff --staged`の両方を確認する理由を説明してください。

> **ヒント：**「git status 見方」「git diff 使い方」「git diff --staged」「git add commit 基本手順」というキーワードを使って調べてください。

### 問題3：複数の変更から記録するものを選ぶにはどうするか

AIに画面の文言修正を依頼したところ、次の3つの変更が作業ディレクトリにあることが分かりました。

- 依頼した画面の文言修正
- AIが追加したデバッグ用の出力
- 自分が途中まで書いている別機能のコード

この状態で、文言修正だけを一つのコミットにするには、何をどの順番で確認し、どのファイルをステージングすればよいでしょうか。すべてをまとめて`git add`する場合と、ファイルを指定して必要な変更だけを選ぶ場合を比較してください。

また、コミット後に作業ディレクトリへ残る変更があってもよいのか、自分の判断と理由を説明してください。

> **ヒント：**「git add ファイル指定」「Git ファイル単位 コミット」「git status staged unstaged」「git diff --staged」というキーワードを使って調べてください。

## 第6章　変更内容の確認

この章では、特にAIが作成・修正したコードを、そのまま受け入れずに確認する方法を学びます。

### 問題1：`git status`と`git diff`では何が分かるのか

`git status`と`git diff`は、どちらも変更を確認するために使いますが、表示する情報は異なります。それぞれで何が分かり、何が分からないのかを比較してください。

さらに、次の3種類の変更を確認するには、どのコマンドやオプションを使えばよいか調べてください。

- 変更されたファイルの一覧
- まだステージングしていない変更の具体的な内容
- すでにステージングした変更の具体的な内容

確認したいことに応じてコマンドを使い分ける必要があるのはなぜか、自分の言葉で説明してください。

> **ヒント：**「git status git diff 違い」「git diff 見方」「git diff --staged」「Git staged unstaged 確認」というキーワードを使って調べてください。

### 問題2：意図していない変更をどのように見つけるのか

AIへ「ボタンの色だけを変更して」と依頼したところ、`git status`には6個の変更ファイルが表示されました。画面上ではボタンの色が正しく変わっています。

この変更をコミットする前に、どのような順番で調べますか。次の観点を含む確認手順を作ってください。

- 変更されたファイルの名前と役割
- 追加・削除されたコードの内容
- 依頼と関係のない変更
- 新しく追加されたファイル
- 設定ファイルや依存関係の変更

未追跡の新規ファイルは、`git status`には表示されても通常の`git diff`には内容が表示されない場合があります。ファイル名だけでなく、中身をどのように確認するかも説明してください。

「画面が正しく見えること」だけでは確認として不十分な理由と、不明な変更を見つけたときにどう対応するかも説明してください。

> **ヒント：**「Git 変更ファイル 一覧」「git status --short」「Git untracked file diff」「git diff --stat」「AI生成コード レビュー」というキーワードを使って調べてください。

### 問題3：大量の変更を安全に確認するにはどうするか

AIが20個のファイルを変更し、差分が長すぎて一度に理解できない状況を想定してください。

どのような単位と順番で確認すれば、重要な変更や危険な変更を見落としにくくなるでしょうか。次の観点を使って、自分用の確認チェックリストを作ってください。

- 変更ファイルの全体像
- 依頼した目的との関係
- 設定、認証、データ削除など影響の大きい箇所
- 自動テストと手動確認
- コミット前とマージ前の再確認

変更が多すぎて自分で説明できない場合、そのまま一つのコミットやマージに進むべきか、自分の判断基準も書いてください。

> **ヒント：**「大きなdiff レビュー 方法」「git diff --stat」「コードレビュー チェックリスト」「AIコード 変更確認」というキーワードを使って調べてください。

## 第7章　コミットの作り方

この章では、後から見ても変更の目的が分かる、扱いやすいコミットの作り方を考えます。

### 問題1：いつコミットするのがよいか

コミットするタイミングについて、「作業がすべて終わった最後に一度だけコミットする方法」と「意味のある区切りごとにコミットする方法」を比較してください。

ログイン画面を作る作業を、画面の作成、入力チェックの追加、テストの追加という3段階に分けた場合、どの時点でコミットしますか。各コミットの時点で、動作確認や変更内容の確認をどこまで行うかも説明してください。

コミットが細かすぎる場合と大きすぎる場合に、それぞれどのような困りごとがあるかを調べ、自分なりの適切なタイミングをまとめてください。

> **ヒント：**「Git コミット タイミング」「小さなコミット メリット」「atomic commit」「コミット 単位」というキーワードを使って調べてください。

### 問題2：分かりやすいコミットメッセージとは何か

次のコミットメッセージを比較し、後から履歴を読む人にとって何が分かりやすく、何が不足しているかを説明してください。

- `修正`
- `いろいろ変更`
- `ログインボタンを押しても反応しない問題を修正`
- `入力が空のとき送信ボタンを無効化`

良いコミットメッセージに含めるとよい情報と、コードを見れば分かるため必ずしも書かなくてよい情報を調べてください。

最後に、AIが作った変更をコミットする場合を想定し、AIが作成したという事実だけでなく、変更の目的、利用者への影響、確認した内容が伝わるメッセージを3つ自分で作ってください。

> **ヒント：**「Git コミットメッセージ 書き方」「良いコミットメッセージ 例」「commit message why」「AI生成コード コミット」というキーワードを使って調べてください。

### 問題3：複数の目的が混ざった変更をどう分けるか

作業中の変更に、次の内容が混ざっている状況を想定してください。

- 新しい検索機能の追加
- 関係のない誤字の修正
- AIが行ったコード全体の整形
- 検索機能のテスト追加

これらを一つのコミットへまとめた場合、レビュー、原因調査、変更の取り消しにどのような影響があるでしょうか。どのような単位に分けてコミットするか、自分の案と理由を説明してください。

すでに変更が混ざっている場合に、ファイル単位または変更箇所単位でステージングする方法も調べてください。分ける途中で内容を壊さないために、何を確認するかも書いてください。

> **ヒント：**「Git コミット 分ける」「git add -p 使い方」「atomic commit」「コミット レビューしやすい」というキーワードを使って調べてください。

## 第8章　変更を元に戻す方法

この章では、変更がどこまで記録されているかを確認し、安全な方法を選んで元に戻す考え方を学びます。

### 問題1：編集中の変更とステージングをどう取り消すのか

対象は、すでにGitで追跡されているファイルとします。まだコミットしていない変更について、次の2つの状況の違いを説明してください。

- ファイルを編集したが、まだ`git add`していない
- ファイルを編集し、すでに`git add`した

`git restore <ファイル>`は、ステージングしていない編集を失わせる可能性があり、その内容は通常Gitから復元できません。一方、`git restore --staged <ファイル>`は、変更内容を作業ディレクトリへ残したままステージングだけを取り消します。この違いを調べ、次の2つの操作方法を説明してください。

- 変更内容を残したままステージングだけを取り消す
- ステージングしていない編集を破棄する

操作前に`git status`や`git diff`で何を確認すべきでしょうか。元に戻した変更を後から使う可能性がある場合に、別の場所へコピーするなどの退避をせず、すぐ取り消してよいかも考えてください。また、未追跡ファイルには通常の`git restore`を使えないことも確認してください。

> **ヒント：**「git restore 変更 取り消し」「git restore --staged」「Git 未コミット 変更 確認」「git diff staged」というキーワードを使って調べてください。

### 問題2：共有済みのコミットを安全に打ち消すにはどうするか

GitHubへ送信済みのコミットに不具合が見つかり、すでに別の人もその履歴を使っている状況を想定してください。

`git revert`がどのような仕組みで変更を打ち消すのかを調べ、「元のコミットを履歴から消すこと」との違いを説明してください。

共有された履歴では、なぜ過去を書き換える操作が問題になりやすいのでしょうか。`revert`を使った後に、差分、テスト、コミット履歴について何を確認するかも含め、安全な対応手順をまとめてください。

> **ヒント：**「git revert とは」「Git 共有履歴 書き換え」「revert reset 違い」「git revert 確認」というキーワードを使って調べてください。

### 問題3：`restore`、`revert`、`reset`をどう使い分けるか

問題1と問題2の復習として、`git restore`と`git revert`が主に何を操作するのかを短く整理してください。そのうえで、この問題ではコミットを指定して履歴を動かす`git reset [--soft|--mixed|--hard] <コミット>`に範囲を絞って調べます。

`git reset`の`--soft`、`--mixed`、`--hard`では、コミット、ステージングエリア、作業ディレクトリがどのように変化するか比較してください。

次の状況ごとに、`restore`、`revert`、コミットを指定する`reset`のどれを選ぶか、理由とともに答えてください。

- コミット前の不要な編集を捨てたい
- ステージングだけをやり直したい
- 自分だけが使っている直前のコミットをやり直したい
- GitHubで共有済みのコミットを打ち消したい

直前のコミットをやり直す方法には`git commit --amend`など、状況によって別の選択肢もあります。必ず一つのコマンドだけが正解とは限らないことを踏まえて判断してください。

特に`git reset --hard`は、追跡されているファイルの未コミット変更を失わせる可能性があります。共有済みの履歴には安易に使わず、影響を判断できない場合は実行せずに詳しい人へ相談してください。実行前に必要な確認も説明してください。

> **ヒント：**「git restore revert reset 違い」「git reset soft mixed hard」「git reset --hard 危険」「Git 共有履歴 戻す」というキーワードを使って調べてください。

- `git diff <コミットA> <コミットB>`
- `git blame <ファイル>`

`git blame`は各行が最後に変更されたコミットを調べる機能であり、表示された人が不具合の責任者だと断定する道具ではありません。コマンドの結果だけで原因を決めつけず、変更の目的や周辺のコードも確認する必要がある理由を書いてください。

> **ヒント：**「git log 見方」「git show 使い方」「git diff commit 比較」「git blame 意味」というキーワードを使って調べてください。

### 問題3：AIへGitの問題を安全に相談するにはどうするか

AIへ「Gitでエラーが出ました。直してください」とだけ伝えた場合、AIは現在のリポジトリの状態や、残したい変更を正確に判断できません。

AIへ相談するときに伝える情報のひな型を作ってください。次の内容を含め、各項目が必要な理由も説明してください。

- 実現したいことと、実行したコマンド
- エラーメッセージ全文
- `git status`の結果と現在のブランチ
- 直前の操作と、共有済みの履歴かどうか
- 残したい未コミットの変更があるか
- 自分がすでに試したこと

相談内容にリモートURL、利用者名、ファイルパス、コミットメッセージなどが含まれる場合、公開してよい情報か確認し、APIキーやアクセストークンなどの機密情報は必ず伏せる必要があります。

強制`push`とは、リモート側の履歴を通常の安全確認を越えて更新し、他の人が基準にしていたコミットを履歴上から外す可能性がある操作です。

最後に、AIから`reset --hard`、強制`push`、ファイル削除などの提案を受けた場合に、実行前に何を質問し、何を確認するか、自分用の安全ルールを作ってください。対象ブランチ、共有済みの履歴か、失われる可能性がある変更やコミット、他の人への影響、退避・復旧方法を含めてください。

> **ヒント：**「AI Git エラー 質問 方法」「git status 共有 注意」「Git コマンド 実行前 確認」「git reset hard force push 危険」というキーワードを使って調べてください。
