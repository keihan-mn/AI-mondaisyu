# Git初心者向け学習問題

この教材は、Gitを使ったことがない初心者が、自分で情報を調べ、具体例や自分の意見を文章にまとめるための学習問題です。

## 回答するときの共通ルール

各問題について、次の内容を含めて回答してください。

1. 調べて分かったこと
2. 初心者にも伝わる、自分の言葉での説明
3. 自分で考えた具体例
4. 自分の意見や判断と、その理由
5. 参考にした情報源

---

## 第1章　Gitの基本知識

### 問題1：Gitは何のために使うのか

Gitとは、何を記録し、どのような問題を解決するための道具でしょうか。「バージョン管理」の意味を調べてください。

そのうえで、ファイルを「完成版」「完成版2」「最終版」のように名前を変えて保存する方法と、Gitを使って変更履歴を管理する方法を比較してください。

Gitを使わずにプログラムを開発した場合に起こりそうな問題について、具体例を挙げて説明してください。

> **ヒント：**「Git バージョン管理とは」「Git 変更履歴」「Gitを使うメリット」というキーワードを使って調べてください。

### 問題2：変更をコミットするまでに何をするのか

Gitでは、ファイルを変更しただけでは、その変更がGitの履歴として記録されたことにはなりません。

ファイルを変更してから、その変更を「コミット」として記録するまでの基本的な流れを調べてください。次の3つの段階がそれぞれ何を意味するのか説明してください。

1. ファイルを変更する
2. 現在の変更状態を確認し、記録する変更を選ぶ
3. 選んだ変更をコミットとして記録する

また、通常の上書き保存とGitのコミットには、どのような違いがあるか説明してください。

最後に、AIにコードの変更を依頼する前に一度コミットしておくと、どのような利点があるか考えてください。

> **ヒント：**「Git 作業の流れ」「git status」「git add」「git commit」「ステージング」というキーワードを使って調べてください。

### 問題3：GitとGitHubは何が違うのか

GitとGitHubは、それぞれ何をするためのものでしょうか。両者の違いを調べ、GitはGitHubがなくても使えるのか説明してください。

また、次の操作にはどのような違いがあるか調べてください。

- 自分のパソコン上でコミットする
- GitHubへ変更内容を送信する

自分一人でバイブコーディングをする場合でもGitHubを利用する利点と、コードを公開・保存するときの注意点をまとめてください。

> **ヒント：**「Git GitHub 違い」「ローカルリポジトリ」「リモートリポジトリ」「git push」「GitHub APIキー 公開」というキーワードを使って調べてください。

## 第2章　ブランチに関して

この章では、次の用語を使用します。

- `main`：開発の基準となる、本線のブランチに一般的に使われる名前
- 作業ブランチ：新機能の追加や不具合の修正など、特定の作業を行うために本線から分けて作るブランチ

### 問題1：ブランチはなぜ必要なのか

Gitにおける「ブランチ」とは何かを調べてください。

AIに新しい機能を作らせる場合を例に、次の2つの進め方を比較してください。

- `main`上で直接コードを変更する
- `main`から作業ブランチを作り、そのブランチ上でコードを変更する

AIの変更が失敗した場合や、期待した結果にならなかった場合、どちらが対処しやすいでしょうか。理由とともに説明してください。

> **ヒント：**「Git ブランチとは」「mainブランチ」「作業ブランチ」「Git ブランチ メリット」というキーワードを使って調べてください。

### 問題2：ブランチを作ってから統合するまでに何をするのか

新しい機能を追加するために、作業ブランチを作ってから、その変更を`main`へ統合するまでの基本的な流れを調べてください。

次の操作を、実際に行う順番に並べて説明してください。

- 現在使用しているブランチを確認する
- `main`から新しい作業ブランチを作る
- 使用するブランチを切り替える
- ファイルを変更する
- 変更内容を確認する
- 変更をコミットする
- 作業ブランチの変更を`main`へ統合する

また、現在使用しているブランチを確認せずに作業を始めると、どのような問題が起こるか考えてください。

> **ヒント：**「git branch」「git switch」「Git 現在のブランチ 確認」「ブランチ コミット マージ 流れ」というキーワードを使って調べてください。

### 問題3：どのようなときに作業ブランチを作るべきか

次の作業を行う場合、新しい作業ブランチを作るべきか、それとも`main`上で作業してもよいかを判断してください。

- 画面上の小さな誤字を修正する
- ログイン機能を追加する
- AIが提案した大規模な変更を試す
- 原因の分からない不具合を調査する
- 複数のファイルにまたがるデザイン変更を行う

この問いに一つの正解はありません。次の観点から、それぞれの判断理由を説明してください。

- 変更の大きさ
- 失敗した場合の影響
- 元に戻しやすいか
- 他の作業と分ける必要があるか
- AIの変更を安全に試せるか

> **ヒント：**「Git ブランチ 使い分け」「feature branch」「ブランチを切る タイミング」「Git AI 開発 ブランチ」というキーワードを使って調べてください。

## 第3章　マージに関して

### 問題1：マージとはどのような操作か

Gitにおける「マージ」とは、あるブランチの変更を別のブランチへ取り込む操作です。

「ログイン機能を作るための作業ブランチ」を例に、次の内容を説明してください。

1. どのブランチでログイン機能を作るのか
2. どのブランチの変更を、どのブランチへ取り込むのか
3. マージした後、`main`はどのような状態になるのか

また、マージすることと、GitHubへ変更を送信することは同じ操作なのか調べてください。

> **ヒント：**「Git mergeとは」「ブランチをmainにマージ」「マージ 取り込む方向」「merge push 違い」というキーワードを使って調べてください。

### 問題2：通常の変更をマージする前に何を確認するべきか

自分で作成した作業ブランチを`main`へマージする前に、確認すべきことを5つ挙げてチェックリストを作ってください。

チェックリストには、次のような観点を含めてください。

- 予定していた変更だけが含まれているか
- プログラムが正常に動くか
- 既存の機能が壊れていないか
- 必要な変更がコミットされているか
- `main`へ取り込んでも問題がない状態か

それぞれについて、「何を確認するか」だけでなく、「確認しなかった場合に何が起こり得るか」も説明してください。

最後に、5つのうち最も重要だと思う確認項目を一つ選び、その理由を書いてください。

> **ヒント：**「Git マージ前 確認」「git status」「git diff」「Git テスト マージ前」「コミット漏れ 確認」というキーワードを使って調べてください。

### 問題3：AIが作った変更をマージしてよいか

AIに一つの機能追加を依頼したところ、予想より多くのファイルが変更されました。画面上では、依頼した機能が正常に動いているように見えます。

この変更を、そのまま`main`へマージしてよいでしょうか。次の観点から、AIが作った変更に特有の危険を調べてください。

- 依頼と関係のないファイルが変更されていないか
- 既存の機能に影響がないか
- セキュリティ上の問題がないか
- 不要なライブラリが追加されていないか
- パスワードやAPIキーが含まれていないか
- 内容を説明できないコードが追加されていないか

最終的に、どのような条件を満たせばマージしてよいと判断するか、自分なりの基準をまとめてください。

> **ヒント：**「AI生成コード レビュー」「Git 変更ファイル 確認」「依存関係 セキュリティ」「APIキー Git コミット」「コードレビュー チェック項目」というキーワードを使って調べてください。

## 第4章　コンフリクトに関して

### 問題1：コンフリクトはなぜ発生するのか

Gitにおける「コンフリクト」とは、Gitが複数の変更を自動では一つに決められない状態です。

次の2つの場合を比較してください。

- 同じファイルの離れた場所を、別々のブランチで変更した場合
- 同じファイルの同じ行付近を、別々のブランチで異なる内容に変更した場合

同じファイルを編集しても、必ずコンフリクトするとは限りません。どのような場合にGitが自動で変更を統合でき、どのような場合に人間の判断が必要になるのか説明してください。

> **ヒント：**「Git コンフリクト 原因」「同じファイル コンフリクト」「Git 同じ行 変更」「Git 自動マージ」というキーワードを使って調べてください。

### 問題2：コンフリクトをどのように解決するのか

コンフリクトが発生したファイルには、Gitが判断できなかった変更箇所を示す記号が表示されます。その記号が何を表しているのか調べてください。

また、コンフリクトの解決方法は「どちらか一方を選ぶ」だけではありません。次の3つの方法について、どのような場合に選ぶか考えてください。

- 一方の変更だけを残す
- 両方の変更を組み合わせる
- 両方を参考にして、新しい内容へ書き直す

コンフリクトを示す記号を削除しただけでは、解決が完了したとはいえないのはなぜでしょうか。解決後に必要な確認も説明してください。

> **ヒント：**「Git コンフリクト 解決」「コンフリクトマーカー」「`<<<<<<<` `=======` `>>>>>>>`」「Git conflict both changes」「コンフリクト解決後 テスト」というキーワードを使って調べてください。

### 問題3：コンフリクトを減らすにはどうすればよいか

コンフリクトは、必ず避けなければならない失敗なのでしょうか。それとも、複数の変更を統合するときに起こり得る通常の出来事なのでしょうか。

次の2つの場合に分けて、コンフリクトを減らすためのルールを考えてください。

- 一人でAIと一緒に開発する場合
- 複数人で開発する場合

変更を小さく分ける、こまめにコミットする、作業範囲を分ける、変更前に最新の状態を確認するといった方法を調べ、自分が特に重要だと思うルールと、その理由を説明してください。

> **ヒント：**「Git コンフリクト 防ぐ」「小さくコミット」「Git 最新状態 取り込む」「チーム開発 作業範囲」「AIコーディング コンフリクト」というキーワードを使って調べてください。
