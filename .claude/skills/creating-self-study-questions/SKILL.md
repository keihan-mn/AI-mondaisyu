# 自主勉強課題の作成

バイブコーディング初心者が自分で調べ、理解した内容と自分の意見を文章にするための問題を作る。用語暗記だけで終わらせず、具体例・比較・判断まで求める。

## 依存

- 保存先と既存課題: `02-自主勉強課題/`
- Git課題の作例: `02-自主勉強課題/01-Git/README.md`
- 配置先: このリポジトリの `.claude/skills/`
- 評価シナリオ: [references/evaluation-scenarios.md](references/evaluation-scenarios.md)

既存課題は難易度や書きぶりの参考にする。既存課題の章構成や問題数を、新しいテーマへ無条件にコピーしない。

このチェックリストをコピーして進める。

- [ ] レビューを反映して重複・飛躍・誤解を修正する

### 1. 要件を特定する

対象者は原則としてバイブコーディング初心者とする。ユーザーが別の経験水準を明示した場合のみ、その指定を優先する。

会話から次を拾う。

- 学習テーマ
- 対象者に関する追加条件
- 章や大項目
- 各章の問題数
- バイブコーディングなど、関連づける実践場面
- 出力先

未指定部分は既存課題を参考に妥当な既定値を置く。結果を大きく左右する情報だけが不明な場合に質問する。

### 2. 学習順序を設計する

原則として、概念、基本的な作業の流れ、使い分け、失敗への対処、自分なりの判断基準の順に難しくする。

初出の専門用語は問題文の前か問題文中で短く説明する。後の問題で必要になる用語や操作を、説明なしで先に使わない。

### 3. 問題を作る

各問題は、調査結果の転記だけでは完答できない形にする。テーマに応じて、次の要素を組み合わせる。

- 用語や仕組みを自分の言葉で説明する
- バイブコーディング初心者にも分かる具体例を作る
- 複数の方法や状況を比較する
- 自分ならどう判断するかを理由とともに述べる
- 参考にした情報源を示す

一つの問題へ論点を詰め込みすぎない。判断に唯一の正解がない問いでは、そのことを明記する。

### 4. キーワードのヒントを付ける

各問題の末尾に、検索へそのまま使える語句を付ける。

```markdown
> **ヒント：**「キーワード1」「キーワード2」「キーワード3」というキーワードを使って調べてください。
```

キーワードは問題文中の未知語、比較対象、実践上の注意を中心に選ぶ。答えそのものや、特定の結論へ誘導する表現は入れない。

### 5. サブエージェントでレビューする

草案全体を渡し、対象者と学習目的を明記してレビューを依頼する。最低限、次を確認させる。

- バイブコーディング初心者が問いの意味を理解できるか
- 未説明の用語や前提知識の先取りがないか
- 学習順序に飛躍がないか
- 問題同士に重複がないか
- 誤解を招く表現や事実上の誤りがないか
- 調べた情報に加えて、自分の考えを書く余地があるか
- ヒントが検索に役立ち、答えを与えすぎていないか
- 指定された実践場面とのつながりがあるか

指摘はそのまま採用せず、ユーザーの目的と照らして反映する。重要な変更点がある場合は、草案との違いが分かるように伝える。

### 6. Markdownへ保存する

ユーザーが保存を依頼した場合、指定先を優先する。指定がなければ `02-自主勉強課題/` 配下の既存構造を調べ、テーマに合うフォルダーを提案する。

保存前に同名ファイルの有無を確認する。既存ファイルに内容がある場合は、明示的な許可なしに上書きしない。保存だけを依頼されていない段階では、草案を会話上で提示する。

標準のファイル名は `README.md` とする。ただし、ユーザーが別名を指定した場合は従う。

### 7. 検証する

保存後、次を確認する。

- 指定した章と問題数がそろっている
- すべての問題にヒントがある
- 初出の専門用語が説明されている
- 見出し階層と番号が一貫している
- 自習問題ビューアーが解析できるよう、章は `##`、各回答対象は `### 問題N`（`N` は章内の連番）になっている
- 各問題のヒントが、その問題内の末尾に `> **ヒント：**` で始まる引用として置かれている
- 保存先がユーザーの指定と一致している
- 既存ファイルを無断で変更・削除していない

ビューアー互換性の確認では、章見出しより前に教材説明を置き、必要に応じて `## 回答するときの共通ルール` を置く。問題文の途中に別の `###` 見出しを入れない。問題番号を変更すると下書きの対応先が変わるため、公開済み問題では既存の章番号・問題番号を維持する。

問題があれば修正して再確認する。完了報告では、作成したファイルへのリンクと、レビューで行った主な改善を簡潔に伝える。

## 標準構成

内容に応じて調整してよいが、基本は次の形にする。

```markdown
# 主題に合ったタイトル

[教材の目的と対象者]

## 回答するときの共通ルール

[回答へ含める内容]

## 第1章　章題

### 問題1：問いの題名

[調べる内容、比較や具体例、自分の判断を求める問題文]

> **ヒント：**「キーワード1」「キーワード2」「キーワード3」というキーワードを使って調べてください。
```

## よくある失敗

| 失敗 | 対処 |
|------|------|
| 専門用語を説明せずに使う | 初出時に短く説明し、詳しい理解は問題として調べさせる |
| 用語の定義だけを答えさせる | 比較、具体例、判断理由のいずれかを加える |
| 似た確認問題が複数ある | 一方を基本手順、もう一方を特有の危険や判断へ分ける |
| ヒントが回答になっている | 検索語だけを示し、結論は学習者に委ねる |
| 例外を省いて誤解を生む | 「必ず」「すべて」などの断定を検証し、条件を示す |
| 草案をすぐ保存する | 保存依頼または承認を確認してから書く |
| 指定先を取り違える | 書き込み前と保存後の両方で絶対パスを確認する |
